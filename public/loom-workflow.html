System Overview — WARP + LOOM + TRUE

WARP

Readiness Gate

Scores every task on 4 dimensions before LOOM execution begins. Flags gaps for Phase 2 resolution.

4 Dimensions

  • 1. Task Definition (clear objective?)
  • 2. Acceptance Criteria (measurable?)
  • 3. Scope Signals (bounded?)
  • 4. Codebase Context (prior art?)

LOOM

8-Phase Execution Loop

Livefront Orchestrated Operations Model. Single-task, worktree-isolated execution from setup through handoff.

8 Phases

Setup → Understand → Clarify → Scope → Plan → Build → Verify → Handoff

TRUE

Drift Detection

Scans for drift between CLAUDE.md pointers, guardrail freshness, and exec-plan state. Run weekly or after sprints.

Checks

  • • CLAUDE.md pointers still valid?
  • • Guardrails still fresh?
  • • Failure Memory complete?
  • • Exec-plans in correct state?

LOOM Phase Details

WARP — Readiness Gate

Pre-flight

Before LOOM begins

Scores every incoming task on 4 dimensions (0–1 each). Tasks scoring < 2.0 are sent back for refinement. Gaps are recorded for Phase 2 resolution.

Scoring

  • 1. Task Definition — clear objective and type
  • 2. Acceptance Criteria — measurable "done"
  • 3. Scope Signals — bounded complexity
  • 4. Codebase Context — prior art and affected files

Inputs → Outputs

Jira ticket → Readiness score + gap list + WARP intake summary

Phase 0 — Setup

LOOM

Initialize execution environment

Creates the LOOM-ANCHOR (compaction-safe checkpoint), sets up a git worktree for isolation, audits CLAUDE.md for guardrails, and detects available companion skills.

Setup checklist

  • • LOOM-ANCHOR created or resumed
  • • Worktree: git worktree add ../jsx-{id} -b daisy/JSX-{id}
  • • CLAUDE.md guardrails loaded (6 hard stops)
  • • Skills detected: TDD build, Figma MCP, acli-jira

Inputs → Outputs

WARP intake → Worktree + anchor + guardrails loaded

Phase 1 — Understand

LOOM

Deep-read the codebase

Maps affected files, reads prior art and completed work from CLAUDE.md. Builds a mental model of the codebase surface area relevant to the task.

Inputs → Outputs

Task definition → Codebase context map, affected file list, prior art references

Phase 2 — Clarify

Interactive

Resolve ambiguity with the engineer

Addresses every gap flagged by WARP. Uses AskUserQuestion to get engineer decisions on budget, scope boundaries, technical approach, and acceptance criteria.

Rule

LOOM does not guess. Every ambiguity is resolved here before scoping.

Inputs → Outputs

WARP gap list → All gaps resolved with engineer decisions

Phase 3 — Scope & Guardrails

Guardrails

Define boundaries, check for hard stops

Defines in-scope / out-of-scope boundaries. Checks every planned change against the 6 CLAUDE.md guardrails. Guardrail contact = STOP and escalate immediately.

6 Guardrails (CLAUDE.md)

  1. BFF credentials server-side only (no Navitaire keys in client code)
  2. Auth middleware changes require human review
  3. Booking step order defined in lib/booking/steps.ts only
  4. Session storage secrets never server-logged
  5. WCAG 2.1 AA mandatory (axe-core)
  6. Figma design match for all UI work

Phase 4 — Plan (Exec-Plan)

Hard Gate

Draft plan → Human approval required

LOOM drafts a step-by-step exec-plan and commits it to docs/exec-plans/active/{slug}.md. The engineer must Approve, Redirect, or Reject before Phase 5 begins. No auto-approve.

Gate Options

  • Approve → Proceed to Phase 5 Build
  • Redirect → Adjust plan, re-present
  • Reject → Return to WARP for re-scoping

Inputs → Outputs

Scope + codebase context → docs/exec-plans/active/{slug}.md (approved)

Phase 5 — Build (TDD)

LOOM + /loom-tdd-build

Test-first implementation per exec-plan step

Custom Phase 5 replacement using /loom-tdd-build skill. Strict RED → GREEN → REFACTOR discipline. Vertical slices only — one test, one implementation, repeat. Never write all tests first.

TDD Cycle (per exec-plan step)

  1. RED — Write a failing test (behavior, not implementation)
  2. GREEN — Minimal code to make it pass
  3. REFACTOR — Clean up (never refactor while red)
  4. Figma MCP check (UI steps only)
  5. Emit LOOM-STEP marker with test counts
  6. Repeat for next step

Anti-patterns (blocked)

No horizontal slicing, no speculative code, no skipping RED, no mocking internals, no silent scope expansion

Phase 6 — Verify

LOOM

Self-verification + CI validation

Checks every acceptance criterion from the exec-plan. Runs full CI suite: npm test, npx tsc --noEmit, npx next lint. All must pass before handoff.

Inputs → Outputs

Implemented code + tests → Verification report (pass/fail per criterion)

Phase 7 — Handoff

LOOM + Human

Commit, PR, Jira update, exec-plan archive

Creates commit and PR (or provides manual instructions). Moves exec-plan from active/ to completed/. Updates Jira ticket to "In Review" and links the PR. Delivers handoff summary.

Handoff Checklist

  • • Commit & push to feature branch
  • • Create PR with summary + test plan
  • • Jira → "In Review" + PR link
  • • Exec-plan: active/ → completed/
  • • Clean up LOOM-ANCHOR sentinel

TRUE — Drift Detection

Periodic

Weekly or after sprints

Scans for configuration drift between LOOM runs. Ensures CLAUDE.md pointers are valid, guardrails are fresh, failure memory is complete (after 20+ merged PRs), and no exec-plans are stuck in active/.

Flags raised if

  • • CLAUDE.md file paths point to deleted files
  • • Guardrail files were modified without review
  • • Failure Memory section missing on mature repos
  • • Exec-plans stuck in active/ for > 2 weeks

Per-task execution (single-task model)

  1. WARP scores the Jira ticket on 4 readiness dimensions
  2. Phase 0 creates worktree, loads guardrails, detects skills
  3. Phase 1 deep-reads codebase, maps affected files
  4. Phase 2 resolves all WARP gaps via engineer interaction
  5. Phase 3 defines scope boundaries, checks guardrails
  6. Phase 4 drafts exec-plan → human approval gate
  7. Phase 5 implements via TDD (RED → GREEN → REFACTOR per step)
  8. Phase 6 self-verifies + runs CI (npm test, tsc, lint)
  9. Phase 7 commits, creates PR, updates Jira, archives exec-plan
Compaction Safety

LOOM-ANCHOR markers at every phase boundary survive context compaction. If the context window fills mid-task, LOOM can resume from the last anchor.

Scope Change Protocol

If implementation reveals unexpected scope: STOP immediately. Do not silently expand. Flag to engineer, get approval, then update exec-plan before continuing.
