Skill Details

/grill-me

Human + Claude

Phase 1 — Discovery & Design

Interview the human relentlessly about a plan or design, walking each branch of the decision tree. Claude provides recommended answers and checks the codebase when questions can be answered by code.

When to use

You have a rough plan (e.g., "real payment gateway") and want it stress-tested before investing in a PRD.

Inputs → Outputs

Conversation context → Shared understanding, resolved decisions

/grill-with-docs

Human + Claude

Phase 1 — Discovery & Design

Same grilling interview as /grill-me, but also enforces domain language from CONTEXT.md. Challenges fuzzy terms, cross-references claims against code, and updates glossary entries & ADRs inline as decisions crystallize.

When to use

Designing a new domain concept (e.g., "fare class", "ancillary") where terminology precision matters and documentation should be updated.

Inputs → Outputs

Plan + domain model → Shared understanding + updated CONTEXT.md + ADRs

/to-prd

Human + Claude

Phase 2 — Planning

Synthesizes the current conversation context and codebase understanding into a formal PRD. Explores the repo, sketches major modules, checks with the user, then writes the PRD using a structured template (problem, solution, user stories, implementation & testing decisions).

When to use

After grilling is complete and the design is solid. Formalizes decisions into a document Ralph can consume.

Inputs → Outputs

Conversation context → docs/prd/<slug>.md

/to-issues

Human + Claude

Phase 2 — Planning

Breaks the PRD into tracer-bullet vertical slices — each is a thin end-to-end cut through all layers (schema, API, UI, tests), independently demoable. Each slice is labelled AFK (Ralph can do it) or HITL (needs human). Dependencies are mapped.

When to use

After the PRD is approved. Creates the task list that Ralph will pick up one-by-one.

Inputs → Outputs

PRD → Task checklist appended to PRD file (per CLAUDE.md — not GitHub Issues)

/tdd

Ralph (mandatory)

Phase 3 — Implementation

Red-green-refactor loop. Write ONE failing test → minimal code to pass → repeat → refactor. Vertical slices only (never write all tests first). Tests verify behavior through public interfaces, not implementation details. Confirms interface design before coding.

When to use

Every implementation task. CLAUDE.md mandates Ralph uses /tdd for all work. Each issue from /to-issues is implemented this way.

Inputs → Outputs

Issue acceptance criteria → Tested, committed code on ralph/prd-N branch

/improve-codebase-architecture

Human + Claude

Ongoing — Architecture Health

Explores the codebase for architectural friction — shallow modules, tight coupling, poor testability. Produces a visual HTML report (Tailwind + Mermaid) with before/after diagrams for each candidate. After you pick one, drops into a grilling session to design the deepening.

When to use

Periodic health check after several features land, or when a part of the codebase feels hard to test or navigate. Findings can loop back into a new /to-prd.

Inputs → Outputs

Codebase → HTML report with deepening candidates → design decisions via grilling

Ralph — The Autonomous Agent

Trigger

./ralph.sh

Branch

ralph/prd-35

Progress

.ralph/progress/

Per-run loop (one issue at a time)

  1. Read PRD parent issue #35 and all child issues on GitHub
  2. Pick highest-priority open child with no open blockers (not labelled in-progress or ralph-done)
  3. Checkout ralph/prd-35 branch
  4. Implement using /tdd — every acceptance criterion met, all tests pass
  5. Reference Figma design system for any UI work (via MCP)
  6. Update CLAUDE.md if architectural decisions were made
  7. Write progress file to .ralph/progress/issue-N.md
  8. Label issue ralph-done on GitHub, post summary comment
  9. Commit & push to ralph/prd-35 — NO PR created
  10. Emit signal: DONE, COMPLETE, or NEED_PERMISSIONS

Run ./ralph.sh repeatedly — each invocation implements exactly one issue. When all issues are done, Ralph emits COMPLETE and stops.
